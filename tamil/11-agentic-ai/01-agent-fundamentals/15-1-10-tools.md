# Tools

> **Learning Path:** Agentic AI
> **Section:** 15.1.10 — Agent fundamentals

### 1. Problem

உங்க agent ஒரு LLM. அது சூப்பர் ஸ்மார்ட், ஆனால் உலகத்தோட கனெக்ட் ஆகல.

User கேட்கிறார்: "எனக்கு கடந்த மாத sales report அனுப்பு, அதுல top 3 customers-ஐ Slack-ல tag பண்ணு".

LLM-க்கு தெரியும் என்ன செய்யணும்னு, ஆனால் அது database-ஐ தொட முடியாது, Slack API-க்கு call பண்ண முடியாது, file generate பண்ண முடியாது.

இதுதான் agent fundamentals-ல முதல் painful point. Reasoning இருக்கு, action இல்ல.

அதனால் agent-க்கு **Tools** தேவை. Tool என்பது agent-க்கு வெளி உலகத்தை தொட உதவும் function/ API.

### 2. Mental Model

Agent = Brain + Tools.

Brain = LLM, reasoning, planning.
Tools = Functions with well-defined input/output.

LLM தனக்கு தெரியாததை tool call ஆக translate பண்ணும். Tool result-ஐ பார்த்து அடுத்த step plan பண்ணும்.

மனதில் வைக்கவேண்டியது: Tool என்பது agent-க்கு கொடுக்கப்பட்ட permission. எந்த tool-ஐ எப்போது use பண்ணுவது என்பதை LLM தான் decide பண்ணும்.

### 3. How It Works

Typical flow:

1. User input → LLM receives
2. LLM decides tool தேவையா? இல்லை direct answer-வா?
3. If tool needed: LLM generates tool name + arguments
4. Agent runtime tool-ஐ execute பண்ணும்
5. Tool result-ஐ LLM-க்கு திருப்பி கொடுக்கும்
6. LLM result-ஐ interpret பண்ணி அடுத்த action எடுக்கும்

முக்கியம்: Tool-களுக்கு schema தேவை. Name, description, parameters with type. இது LLM-க்கு tool-ஐ சரியாக call பண்ண உதவும்.

Example schema:

`get_sales_report`:
- month: string
- year: number

Description: "Fetch sales data from database for given month"

### 4. Architectural Reasoning

Tool எப்போது useful?

* Agent-க்கு external state access தேவைப்படும்போது
* Deterministic, repeatable operation தேவைப்படும்போது
* LLM-ன் knowledge cutoff-க்கு அப்பாற்பட்ட real-time data தேவைப்படும்போது

Alternatives:

* RAG மட்டும்: Read-only knowledge retrieval. Action இல்ல.
* Hardcoded logic in application: Flexible இல்ல, every new capability = code deploy.
* Tools: LLM decides dynamically which tool to use.

Architect choose tools when agent-க்கு autonomy வேண்டும், மற்றும் action space predictable ஆக define பண்ண முடியும்.

### 5. Trade-offs

**Tool sprawl vs usefulness**: Tools அதிகமாக கொடுத்தால் LLM confuse ஆகும், wrong tool தேர்வு செய்யும். குறைவாக கொடுத்தால் capability குறையும்.

**Latency**: Every tool call = network round trip. Multi-step agent = latency multiply ஆகும்.

**Safety**: Tool என்பது side effect. Database delete, payment, email send போன்ற tools-ல தவறான call-க்கு பெரிய impact. Validation, authorization, rate limiting must.

**Hallucination in arguments**: LLM tool name-ஐ சரியாக தேர்வு செய்யலாம், ஆனால் arguments-ல hallucinate செய்யலாம். Schema validation முக்கியம்.

Failure mode: Tool returns error / timeout. Agent அதை handle பண்ண தெரியுமா? Retry logic, fallback தேவை.

### 6. Practical Example

Enterprise support agent.

Tools:
* `search_tickets` - past tickets
* `get_customer_profile` - CRM data
* `create_jira_ticket` - action
* `send_email` - action
* `check_inventory` - product DB

User: "Customer XYZ-க்கு last month refund request status என்ன?"

Agent reasoning:
1. customer_id தேவை → `get_customer_profile` with name XYZ
2. customer_id கிடைத்தது → `search_tickets` with customer_id and refund
3. status found → direct answer

User: "இது escalate பண்ணு"
Agent:
1. `create_jira_ticket` with priority high
2. `send_email` to customer with ticket ID

இங்கே agent-க்கு read tools + write tools இரண்டும் இருக்கு. Write tools use பண்ணும் முன் confirmation prompt பண்ணலாம்.

### 7. Reasoning Challenge

உங்களிடம் sales agent இருக்கு. Tools உள்ளன:
* `get_product_price` - fast, read-only
* `create_order` - slow, writes to DB, irreversible
* `send_promotion_email` - sends email to customer list

User கேட்கிறார்: "Product A-க்கு price சொல்லு, அதை order பண்ணு, மற்ற customers-க்கு promotion mail அனுப்பு".

இங்கே என்ன architectural guardrails வைப்பீர்கள்? எந்த tool-ஐ எப்போது allow பண்ணுவீர்கள்? ஏன்?

### 8. Key Takeaways

* Agent-க்கு brain இருக்கு, tools இல்லாமல் world-ஐ touch முடியாது
* Tool என்பது well-defined function with schema, description, and safe execution boundary
* More tools ≠ better agent. Relevant, safe, and clearly described tools matter
* Every tool call adds latency, cost, and failure surface. Design for idempotency and error handling
* Architectural decision: read tools vs write tools, who can authorize, and how to prevent harmful autonomous actions
