# KEDA

> **Learning Path:** Cloud & Infrastructure Architecture
> **Section:** 5.3.11 — Kubernetes

## Problem

Kubernetes-ல HPA இருக்கு. அது CPU / memory usage பார்த்து scale பண்ணும். 

ஆனா உங்க workload event-driven ஆ இருக்கும். Kafka topic-ல message வரும் போது தான் process பண்ணனும். RabbitMQ queue length அதிகமாகும் போது தான் pod வேண்டும். இரவு 2 மணிக்கு traffic zero.

இப்போ என்ன ஆகும்?
* HPA CPU பார்க்கும். CPU 0% இருக்கும். Scale down ஆகாது. 
* Manual ஆ 3 pod வச்சிட்டா cost waste.
* Scale to zero வேணும்னா? HPA zero-க்கு போகாது.
* Custom metric எழுதி external metrics API-க்கு push பண்ணி HPA-வை கட்டுப்படுத்தலாம். ஆனா அது boilerplate, flaky, ஒவ்வொரு event source-க்கும் தனி code.

இதுதான் painful point. **Event count / queue length / external signal பார்த்து scale பண்ணனும், ஆனா Kubernetes அதை native ஆ தெரியாது.**

## Mental Model

KEDA = Kubernetes Event-driven Autoscaling.

நீங்கள் Kubernetes-க்கு ஒரு translator கொடுக்கிறீர்கள். அது external event source-ஐ பார்த்து "இப்போ X replicas வேண்டும்" என்று சொல்லும். அதை HPA-வுக்கு மாற்றி பேசும்.

Mental model: 
`Event Source -> Scaler -> ScaledObject -> Deployment / Job`

KEDA ஒரு operator + set of scalers. Scaler ஒவ்வொரு queue / database / HTTP source-க்கும் தெரியும்.

## How It Works

Core CRD: `ScaledObject`.

நீங்கள் ஒரு Deployment-க்கு ScaledObject வரையறுக்கிறீர்கள்:
* trigger: kafka, azure-servicebus, prometheus, etc
* metricName, threshold
* minReplicaCount, maxReplicaCount
* scaleToZero போன்ற policy

KEDA operator அந்த ScaledObject-ஐ பார்த்து அதற்குரிய Scaler-ஐ ஆரம்பிக்கும். Scaler தொடர்ந்து event source-ஐ poll / webhook மூலம் கண்காணிக்கும். Desired replica count கணக்கிட்டு, வேண்டுமென்றால் HPA object-ஐ update செய்யும்.

ScaledJob என்பது batch work-க்கு. ஒரு queue இருந்தால் மட்டும் Job spawn ஆகும்.

Cold start உள்ளது. Scale to zero செய்தால் pod இல்லை. முதல் event வந்ததும் pod boot ஆக 5-30s ஆகலாம்.

## Architectural Reasoning

இது useful ஆகும் போது:
* Workload sporadic, bursty, event-driven
* Cost-sensitive, idle time அதிகம்
* Scale to zero தேவை
* External system metrics-ல scale பண்ண வேண்டும்

Constraints addressed:
* **Latency vs Cost**: Traffic இல்லாத போது zero pod, traffic வந்ததும் உடனே scale
* **Coupling**: Application code-ல scaling logic இருக்கக்கூடாது
* **Operability**: ஒரே manifest-ல scaling policy define ஆகும்

Alternatives:
* KNative Eventing / Knative Serving: scale to zero செய்யும், ஆனா request-based, queue-based flow-க்கு complex
* Custom controller எழுதி HPA metrics API-ல push பண்ணுவது: works, ஆனா maintenance overhead
* Over-provision and idle: simple, ஆனா cost high

நீங்கள் KEDA choose பண்ணுவது: **event source variety அதிகம், team Kubernetes-ல இருக்கு, serverless-like behavior வேண்டும், ஆனா Knative full migration வேண்டாம் என்றால்.**

## Trade-offs

**Scale to zero vs Cold start latency**
Zero cost கிடைக்கும். ஆனா முதல் request வந்ததும் cold start. User-facing synchronous path-க்கு இது ஒரு problem. Async worker-க்கு ஓகே.

**Metric reliability**
Scaler external system-ஐ poll பண்ணும். Poll interval, network failure, auth token expiry இருக்கும். Metric stale ஆனால் over/under scale ஆகும்.

**Operational complexity**
இன்னொரு moving part. KEDA operator, scalers, ScaledObject lifecycle. Debugging-க்கு `keda-metrics-apiserver` logs பார்க்க வேண்டும்.

**Scale behavior tuning**
Cooldown period, scaling policies, stabilization windows தவறாக set செய்தால் flapping ஆகும். HPA + KEDA இரண்டும் interact ஆகும்.

Failure mode: Event source down ஆனால் scaler crash ஆகலாம், அப்போ pods stuck ஆகும். External secret rotation miss ஆனால் scaling stop ஆகும்.

## Practical Example

நிறுவனத்தில் payment reconciliation service இருக்கு. Azure Service Bus-ல messages வரும், batch-ஆ process பண்ணனும். பகலில் 10k msg/min, இரவில் 0.

Deployment-க்கு ScaledObject:

trigger type = azure-servicebus
queue length > 50 என்றால் scale up, <10 என்றால் scale down
minReplicaCount = 0, maxReplicaCount = 20
cooldownPeriodSeconds = 30

மாலை 6 மணிக்கு பிறகு pods 0-க்கு போகும். மறுநாள் காலை முதல் message வந்ததும் KEDA scaler தூண்டி 1 pod ஆரம்பிக்கும். Queue build ஆகும் போது replica அதிகரிக்கும்.

Application code-ல எந்த scaling logic இல்லை. Just consume message.

## Reasoning Challenge

உங்களிடம் 20 consumers இருக்கு, எல்லாருக்கும் same Kafka topic தேவை. Consumer processing speed வேறுபடுகிறது. Producer-ஐ block பண்ணக்கூடாது. Replay-ம் வேண்டும்.
