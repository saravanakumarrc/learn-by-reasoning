# CDN

> **Learning Path:** Cloud & Infrastructure Architecture
> **Section:** 5.1.6 — Cloud fundamentals

## 1. Problem

உங்கள் e-commerce site-ன் origin server Singapore-ல இருக்கு. User Chennai-ல இருந்து product page open பண்ணும்போது image load ஆக 400ms - 800ms ஆகுது. அதுவும் flash sale-ல traffic spike வந்தால் origin overload ஆகி error rate ஏறுது. 

இது ஏன்? Request எல்லாம் எப்போவும் அதே origin-க்கு தான் போகுது. Network round trip நீளம், origin bandwidth cost அதிகம், மேலும் static content-க்கு அடிக்கடி அதே request repeat ஆகுது.

இங்கே painful point என்னன்னா: **உள்ளடக்கம் அடிக்கடி மாறாது, ஆனால் ஒவ்வொரு user-க்கும் தனியா fetch பண்ணுறோம்.**

## 2. Mental Model

CDN என்பது உங்கள் content-ஐ பூமி முழுக்க பரப்பி வச்சிருக்கும் cache network.

Think of it as local branch office. நீங்கள் ஒரு புத்தகம் Singapore headquarters-ல வச்சிருக்கீங்க. அதே புத்தகத்தை Chennai, Mumbai, Frankfurt branch-ல copy வச்சுட்டா அங்கே இருக்கும் user உடனே வாங்கிடலாம். Update வந்தால் மட்டும் master copy-க்கு sync பண்ணுவோம்.

CDN-ல் அந்த branch offices தான் PoP - Point of Presence.

## 3. How It Works

User request வரும்போது CDN DNS user-க்கு அருகில் இருக்கும் edge node-க்கு route பண்ணும்.

1. **Cache hit**: Edge-ல content இருந்தால் அங்கிருந்தே serve ஆகும். Origin touch இல்லை.
2. **Cache miss**: Edge origin-க்கு request போகும், content-ஐ fetch பண்ணி cache-ல வச்சுட்டு user-க்கு கொடுக்கும்.
3. **TTL & invalidation**: Content எவ்வளவு நேரம் cache-ல இருக்கணும் என்பதை TTL decide பண்ணும். Update வந்தால் explicit invalidation அல்லது short TTL வச்சு manage பண்ணுவோம்.

Static assets, images, videos, JS/CSS bundles போன்ற immutable content தான் இதற்கு best fit.

## 4. Architectural Reasoning

CDN எப்போது useful?

* **Latency-sensitive read heavy workload**: Global users, media delivery.
* **Origin protection**: Traffic spike-ல origin-ஐ overload ஆகாம தடுக்க.
* **Bandwidth cost குறைக்க**: Origin egress cost குறைவு.

Constraints-ஐ பார்த்தால்:
* Content read-mostly, write-rarely
* Eventual consistency acceptable
* Cacheable via HTTP headers

Alternatives என்ன?
* Origin-ஐ scale பண்ணி anycast IP use பண்ணலாம். ஆனால் bandwidth cost அதிகம், latency முழுமையா solve ஆகாது.
* Regional deployments பண்ணலாம். ஆனால் operational complexity அதிகம்.

ஆர்கிடெக்ட் choose பண்ணுவது ஏன்னா: உங்கள் service-ன் hot path-ல network latency ஒரு constraint ஆகும்போது, compute-ஐ scale பண்ணுவதை விட data-ஐ closer கொண்டு வருவது cheaper மற்றும் faster.

## 5. Trade-offs

* **Freshness vs Speed**: Cache TTL அதிகம் வச்சால் latency குறையும், ஆனால் stale content risk. Invalidation mechanism சரியா இல்லாமல் user-க்கு பழைய version தெரியும்.
* **Cost vs Complexity**: CDN usage cost per GB, PoP coverage வேண்டும். Cache rules, purge logic, cache key design என்பது extra operability.
* **Security**: Edge-ல serve ஆகுறதால் origin IP hide ஆகும். ஆனால் cache poisoning, bypass attempts manage பண்ண வேண்டும்.
* **Failure mode**: Edge node down ஆனால் next closest node take over ஆகும். Origin down ஆனாலும் cached content serve ஆகும், ஆனால் new content fetch முடியாது.

## 6. Practical Example

ஒரு SaaS product-க்கு dashboard-ல 500KB JS bundle, 2MB images.

Origin US-East-ல இருக்கு. India user-க்கு TTFB 280ms.

CDN enable பண்ணியதும்:
* DNS resolve ஆகி nearest PoP Mumbai-க்கு request போகும்.
* First request cache miss, origin fetch, 280ms + cache.
* Next requests 25-40ms-ல serve.
* Flash sale-ல 10x traffic வந்தாலும் origin-க்கு requests 90% குறையும்.

API responses-க்கு CDN பயன்படுத்த மாட்டோம். Because personalized, short TTL, consistency முக்கியம்.

## 7. Reasoning Challenge

உங்களுக்கு live sports streaming site இருக்கு. Video chunks 10 sec duration, மீண்டும் மீண்டும் request வரும். ஆனால் ஒரு premium user-க்கு மட்டும் personalized overlay, stats real-time.

இங்கே CDN எதை cache பண்ணுவீங்க, எதை origin-ல வைப்பீங்க? Cache key-ல என்ன மாற்றம் செய்வீங்க? ஏன்?

## 8. Key Takeaways

* CDN solves **distance and origin load** problem, not compute problem.
* Cacheable, immutable content தான் main win. Dynamic personalized content-க்கு
