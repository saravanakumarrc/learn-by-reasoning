# OOP

> **Learning Path:** Architect's Developer Foundation
> **Section:** 1.1.3 — 1. Programming mastery

## 1. Problem

நீங்கள் 5 வருஷமா வளர்ந்துட்டு வரும் ஒரு e-commerce backend-ஐ maintain பண்ணுறீங்க. ஆரம்பத்துல `calculate_price()` மாதிரி ஒரே function இருந்தது. 

இப்போ:
- வெவ்வேறு tax rules இருக்கு
- Discount வகைகள் வளர்ந்துட்டு இருக்கு
- Coupon, wallet, promo code எல்லாம் mix ஆகுது
- Payment methods: UPI, Card, Netbanking, Wallet

ஒரே file-ல நிறைய if-else, global variables, helper functions. ஒரு rule மாற்றினால் மூன்று இடத்துல break ஆகுது. ஒரு developer தொட, இன்னொருத்தருக்கு side effect தெரியாம போகுது.

**என்ன வலி?** Code duplicate ஆகுது, change பண்ண பயம் வருது, ஒரு feature-க்கு யார் என்ன மாற்றுவாங்கன்னு தெரியல. System boundaries தெளிவா இல்ல.

OOP அதுக்கு ஒரு பதில்.

## 2. Mental Model

OOP-ல நீங்கள் **data + behavior-ஐ ஒன்னா pack பண்ணுறீங்க**.

Real world-ல ஒரு `Order` என்பது அது வச்சிருக்கும் items, total, status மாதிரி state-ஐ மட்டும் வச்சு நிக்காது. அதுக்கு `calculate_total()`, `apply_discount()`, `cancel()` மாதிரி behavior-ம் இருக்கு.

OOP சொல்றது: அந்த state + behavior-ஐ ஒரே unit-ல வச்சு, அதுக்கு பெயர் கொடு. அதை `object`ன்னு கூப்பிடு. பல objects-ஐ உருவாக்க blueprint-க்கு `class`ன்னு பேர்.

முக்கிய mental model இது இல்ல: "inheritance use பண்ணு". முக்கிய model இது: **உன் system-ஐ domain entities-ஆ பிரிச்சு, அவங்க responsibility-ஐ அவங்ககிட்டயே விடு**.

## 3. How It Works

நான்கு ideas மட்டும் முக்கியம். மீதி syntax.

**Encapsulation:** object-ன் internal state-ஐ hide பண்ணு. வெளியிலிருந்து நேரடியா field-ஐ touch பண்ணாம, method மூலமா மட்டும் மாற்று. இதனால invariants protect ஆகும்.

**Abstraction:** implementation-ஐ மறைச்சு, ஒரு clean interface காட்டு. Client-க்கு `payment.process()` போதும், அது UPI-ஆ Card-ஆன்னு தெரிய வேண்டாம்.

**Inheritance / Composition:** ஒரு concept-ஐ மீண்டும் மீண்டும் எழுதாதே. ஆனால் inheritance-ஐ விட composition பெரும்பாலும் safe. `Order` has-a `Payment`, has-a `ShippingAddress`... 

**Polymorphism:** ஒரே interface, வெவ்வேறு behavior. `Discount` interface-க்கு `apply()` method இருக்கு. `FlatDiscount`, `PercentageDiscount` வெவ்வேறு logic வைக்கும். Caller-க்கு தெரிய வேண்டாம்.

```python
class Payment:
    def process(self, amount): ...
    
class UpiPayment(Payment):
    def process(self, amount): # UPI specific

class CardPayment(Payment):
    def process(self, amount): # Card specific
```

## 4. Architectural Reasoning

எப்போ OOP useful ஆகும்?

- Domain complex ஆகி, entities-க்கு life-cycle இருக்கும் போது. `Order`, `Invoice`, `Shipment` மாதிரி.
- Team பெரிசாகும்போது, boundaries clear-ஆ இருந்தா parallel work ஈஸி.
- Long lived business logic, rules தொடர்ந்து மாறும் போது.

Alternative என்ன? Procedural / functional. Small scripts, data transformation pipeline-க்கு procedural clean ஆக இருக்கும். 

Architect decision: நீங்கள் object-ஐ design பண்ணுறதே system boundaries-ஐ define பண்ணுறதுக்கு. ஒரு class என்பது ஒரு responsibility. அதுக்கு மேல வளர்ந்தா split பண்ணு.

## 5. Trade-offs

**Abstraction cost.** Simple CRUD service-க்கு class hierarchy வச்சு over-engineer பண்ணினா, code படிக்க கஷ்டம், performance overhead சின்னது ஆனால் cognitive load அதிகம்.

**Coupling vs Cohesion.** Encapsulation நல்லது, ஆனால் ஒரு class-ல எல்லாத்தையும் வச்சுட்டா God Object ஆகும். அப்புறம் change எங்க வேணா impact.

**Inheritance rigidity.** Deep inheritance tree-க்கு பிறகு change ஒரு இடத்துல பண்ண, யார் பாதிக்கப்படுவாங்கன்னு தெரியாது. Composition தேர்வு செய்ய, flexibility அதிகம்.

Failure mode: நீங்கள் OOP use பண்ணுறீங்கன்னு பேருக்கு `BaseService`, `AbstractManager`
