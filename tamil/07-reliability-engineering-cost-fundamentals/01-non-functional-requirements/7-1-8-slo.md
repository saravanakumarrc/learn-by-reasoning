# SLO

> **Learning Path:** Reliability Engineering & Cost Fundamentals
> **Section:** 7.1.8 — Non-functional requirements

## Problem

உங்கள் service "working" என்று காட்டுகிறது. ஆனால் customers புகார் கொடுக்கிறார்கள்: "checkout slow ஆக இருக்கு", "payment fail ஆகுது".

Team-க்குள் argument: Dev team சொல்கிறது "99% uptime இருக்கு", Product சொல்கிறது "user experience கெட்டு போகுது", SRE சொல்கிறது "எங்களுக்கு எந்த target-ம் தெரியாது".

என்ன பிரச்சனை? Reliability பற்றி எல்லோருக்கும் வெவ்வேறு definition. யாரும் என்ன அளந்து கொண்டிருக்கிறார்கள் என்றே தெரியாது.

இப்படி ambiguous expectation இருந்தால், incident ஆனதும் blame game தான். எப்போது fix பண்ண வேண்டும், எப்போது new feature release பண்ணலாம் என்று யாருக்கும் தெரியாது.

## Mental Model

SLO என்பது **நீங்கள் உண்மையில் அளந்து, commit பண்ணும் ஒரு measurable target**.

SLO = Service Level Objective. இது உள்ளுக்குள் உங்கள் team-க்கு.

SLA என்பது அதை customer-க்கு காட்டும் contract.

எளிமையாக: SLO என்பது "எங்கள் checkout API 99.9% requests 500ms க்குள் complete ஆகும்" என்று சொல்வது. ஒரு எண்ணுடன், ஒரு measurement window-உடன், ஒரு user-facing definition-உடன்.

முக்கியம்: SLO ஒரு வாக்குறுதி மட்டும் இல்லை. அது **error budget** ஐ உருவாக்குகிறது. Error budget = அனுமதிக்கப்பட்ட failure ஆனது.

99.9% availability என்றால் error budget 0.1%. அந்த budget தீர்ந்தால், நீங்கள் reliability-க்கு focus செய்ய வேண்டும், new features stop.

## How It Works

SLO வை மூன்று விஷயங்களால் define பண்ணுங்கள்:

1. **Service & user**: எந்த user journey? எந்த API? எல்லா request-உம் அல்ல, golden path.
2. **Indicator & target**: Availability? Latency? Error rate? Throughput?
3. **Window**: 28 days sliding window பொதுவாக use ஆகும்.

உதாரணம்: `checkout API, 99.9% requests 500ms க்குள், 28 days window`.

அதை மானிட்டர் பண்ணுங்கள். Error budget burn rate பாருங்கள். Fast burn = பிரச்சனை வருகிறது.

## Architectural Reasoning

SLO ஏன் தேவை?

**Constraint address பண்ணுவது**: Unlimited reliability வேண்டும் என்றால் cost infinite. SLO உங்களுக்கு trade-off செய்ய boundary கொடுக்கிறது.

Architect எப்போது choose பண்ணுவார்?
* Multi-team system இருக்கும் போது, shared understanding வேண்டும்.
* Release velocity vs reliability balance தேவைப்படும் போது.
* Cost optimize பண்ண வேண்டும் போது.

Alternative என்ன? "Just keep it up" என்று feel based run செய்வது. அது scale ஆகாது.

SLO உங்களுக்கு decision framework கொடுக்கிறது: Error budget இருந்தால் feature release பண்ணலாம், இல்லையென்றால் hardening.

## Trade-offs

* **Availability vs Latency**: 99.99% availability கேட்டால் latency SLO relax ஆக வேண்டியிருக்கும். Strict latency + high availability = expensive architecture, multi-region, aggressive timeout tuning.
* **Strict SLO = High cost**: 99.9% -> 99.99% என்பது 10x error budget குறைவு. அதற்கு redundancy, better monitoring, faster failover வேண்டும்.
* **SLO அமைப்பது கடினம்**: Business impact-ஐ அளவிடுவது கஷ்டம். Wrong SLO = வேலை வீண். Too loose = user pain ignore. Too strict = team always on fire.
* **Error budget gaming**: Team budget தீர்ந்ததும் work stop செய்ய வேண்டும். Culture இல்லாவிட்டால் SLO paper only.

Failure mode: SLO மட்டும் define பண்ணி, alerting இல்லாவிட்டால் பயனில்லை. SLO without monitoring = wish.

## Practical Example

E-commerce checkout service.

Business goal: conversion.

நீங்கள் இரண்டு SLO வைக்கிறீர்கள்:
1. Availability: 99.95% of successful HTTP 200 responses, 28 days window
2. Latency: 99% of requests < 500ms p99

இதை அளக்கிறீர்கள். மாதம் ஆரம்பத்தில் error budget healthy. அப்போது new payment provider integration release பண்ணலாம்.

மாத நடுவில் latency degrade ஆகி error budget 80% burn ஆனது. இப்போது release freeze. Team
