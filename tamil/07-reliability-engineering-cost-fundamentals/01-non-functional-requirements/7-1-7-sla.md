# SLA

> **Learning Path:** Reliability Engineering & Cost Fundamentals
> **Section:** 7.1.7 — Non-functional requirements

## 1. Problem

நீங்க ஒரு API வெளியிட்டீங்க. Customer சொல்றார்: "உங்க service slow ஆ இருக்கு". உங்க team சொல்றது: "எங்களுக்கு தெரியல, எப்போ slowன்னு".

Production-ல network blip வரும், pod crash ஆகும், DB slow ஆகும். இதை எப்படி define பண்ணுவீங்க? எப்போது அது acceptable, எப்போது incident?

இன்னொரு பக்கம் business சொல்லும்: "99.9% uptime வேணும்". Engineering சொல்லும்: "அது கொடுக்கணும்னா 3x cost ஆகும்". இந்த gap-ஐ பேச ஒரு common language இல்லாம போனால், blame game தான்.

இதை தீர்க்கத்தான் SLA வந்தது. SLA என்பது **promise with numbers**, not a feature list.

## 2. Mental Model

SLA = Service Level Agreement. ஒரு வாடிக்கையாளருக்கு நீங்கள் எவ்வளவு நம்பகமாக service கொடுப்பீங்கன்னு ஒரு measurable contract.

மூன்று layer-ஆல் யோசிக்கவும்:
* **SLO** - Service Level Objective. நீங்கள் உள்ளுக்குள் target பண்ணும் number. எ.கா. 99.95% availability.
* **SLI** - Service Level Indicator. அதை measure பண்ணும் metric. எ.கா. successful request / total request.
* **Error Budget** - SLO miss ஆனால் எவ்வளவு room இருக்கு. 99.9% availability = monthly ~43 minutes downtime allowed.

நீங்க availability-ஐ மட்டும் பேசாமல் latency, error rate, throughput, support response time எல்லாம் define பண்ணலாம்.

## 3. How It Works

SLA ஒரு document அல்ல. அது measurement + consequence combo.

ஒரு typical setup:
Client -> API Gateway -> Service -> DB
Monitoring system SLI-ஐ continuous-ஆ collect பண்ணும். Prometheus/Grafana, CloudWatch போன்றவை.

SLO breach ஆனால் error budget burn ஆகும். Error budget தீர்ந்தால், new feature deploy freeze, only reliability work.

SLA breach-க்கு penalty இருக்கலாம்: service credit, refund.

முக்கியம்: SLA அளவீடு **customer perspective-ல** இருக்கணும். உங்க internal server up ஆனாலும், client-க்கு 5xx வந்தா down தான்.

## 4. Architectural Reasoning

SLA எப்போ useful?
* External customers உள்ள service-க்கு. Payment gateway, SaaS API.
* Internal platform teams-க்கு. Internal SLA வச்சு downstream team-க்கு contract கொடுக்கலாம்.

Constraint address பண்ணுவது:
* Ambiguity remove பண்ணுது. "Good performance" என்பதற்கு பதில் p95 latency < 200ms.
* Capacity planning-க்கு input கொடுக்குது.
* Reliability vs feature velocity trade-off-ஐ quantify பண்ணுது.

Alternative: வெறும் "best effort". அது early stage startup-ல ஓகே. ஆனால் scale ஆனதும், enterprise customer கேட்பார்.

## 5. Trade-offs

**Availability vs Cost.** 99.9% vs 99.99% என்பது 9x cost வித்தியாசம் வரும். Multi-region, redundancy, hot standby எல்லாம் cost.

**Latency vs Consistency.** Strong consistency வேண்டும் என்றால் latency அதிகரிக்கும். SLO-வில் எதை prioritize பண்ணுறீங்க?

**Precision vs Simplicity.** p99 latency track பண்ணுவது expensive. Sampling, cardinality கூடுது. எந்த metric-ஐ track பண்ணுவது என்பது trade-off.

**Failure mode:** SLI சரியா define பண்ணலைன்னா gaming ஆகும். எ.கா. health check endpoint மட்டும் up ஆக இருந்தால் availability 100% காட்டும், ஆனால் real traffic fail ஆகும்.

## 6. Practical Example

உங்களுக்கு ஒரு payment initiation API உள்ளது.

Business கேட்கிறது: success rate > 99.9% and p95 latency < 500ms.

நீங்கள் design பண்ணும்போது:
* Retry with idempotency key வைக்கிறீங்க, timeout 10s.
* Circuit breaker வைத்து downstream bank service fail ஆனால் fast fail பண்ணுறீங்க.
* Read replica use பண்ணி latency குறைக்கிறீங்க.
* Error budget policy: budget > 50% உள்ளது என்றால் மட்டும் new feature release.

ஒரு மாதத்தில் 45 mins downtime வந்தால் SLO breach. அப்போ error budget negative. அடுத்த sprint-ல feature freeze, post-mortem + fix.

Customer-க்கு SLA: 99.9% availability, breach ஆனால் 10% service credit.

## 7. Reasoning Challenge

உங்க service-க்கு இப்போது p95 latency 400ms, p99 latency 2.5s. Customer complain பண்ணுறார்: "என் users-க்கு slow feel ஆகுது".

SLO-ஐ p95 < 500ms ஆக set பண்ணலாமா? அல்லது p99 < 1s ஆக set பண்ணலாமா? ஏன்? அந்த தேர்வு architecture-ல என்ன மாற்றம் கொண்டு வரும்? Cost-ல என்ன impact?

## 8. Key Takeaways

* SLA என்பது vague promise அல்ல, measurable SLI + SLO + error budget.
* SLA உருவாக்குவது reliability vs cost vs velocity trade-off-ஐ explicit ஆக்குகிறது.
* Customer perspective-ல measure பண்ணுங்கள், internal health check மட்டும் போதாது.
* Error budget இருக்கும்போது தான் அர்த்தம
