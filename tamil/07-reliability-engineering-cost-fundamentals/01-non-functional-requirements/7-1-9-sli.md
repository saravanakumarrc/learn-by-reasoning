# SLI

> **Learning Path:** Reliability Engineering & Cost Fundamentals
> **Section:** 7.1.9 — Non-functional requirements

## 1. Problem

உங்கள் service production-ல ஓடிக்கொண்டிருக்கு. Users சொல்கிறார்கள்: "சில நேரம் slow ஆ இருக்கு", "சில நேரம் fail ஆகிறது". 

ஆனால் உங்களுக்கு தெரியவில்லை: slow என்றால் எவ்வளவு slow? fail என்றால் எத்தனை முறை? எப்போது ஆரம்பித்தது?

இந்த vagueness தான் பிரச்சனை. 
Operations team alert போடுகிறது, product team blame செய்கிறது, engineering team "எங்களுக்கு தெரியாது" என்கிறது.

ஒரு system reliable ஆ இருக்கிறதா என்பதை prove செய்ய வேண்டுமென்றால், subjective feeling போதாது. Measurable signal வேண்டும்.

அதற்கு தான் SLI வருகிறது.

## 2. Mental Model

**SLI = Service Level Indicator.** அது ஒரு thermometer மாதிரி.

உடல் வெப்பம் எப்படி உடல் நிலையை காட்டுகிறதோ, அதே போல SLI service health-ஐ காட்டுகிறது.

SLI என்பது நீங்கள் continuously measure செய்யும் metric. 
அதன் மீது SLO target வைக்கிறோம். அதன் மீது SLA commitment கொடுக்கிறோம்.

```
SLI measurable signal -> SLO target -> SLA contract
```

முக்கியமானது: SLI என்பது business-க்கு முக்கியமான behaviour-ஐ தான் measure செய்ய வேண்டும்.

## 3. How It Works

SLI-ஐ தேர்வு செய்யும் போது மூன்று கேள்விகள்:

1. **என்ன measure செய்கிறோம்?** - Availability, Latency, Error rate, Throughput, Freshness...
2. **எப்படி define செய்கிறோம்?** - Good request vs bad request.
3. **எங்கே measure செய்கிறோம்?** - Client side, server side, synthetic.

உதாரணத்திற்கு, API availability SLI:

`successful requests / total requests`

இங்கே successful என்பதை நீங்கள் define செய்ய வேண்டும். HTTP 2xx மட்டுமா? 3xx உம் சேருமா? Timeout எப்படி கணக்கிடுவது?

Latency SLI:

`p95 request latency < 300ms`

Good request என்பது 300ms-க்குள் முடிந்த request.

இந்த definition தெளிவாக இல்லாவிட்டால், dashboards ஒன்றுக்கொன்று முரண்படும்.

## 4. Architectural Reasoning

SLI தேவைப்படுவது ஒரு service-க்கு இரண்டு dependencies இருக்கும் போது தான்.

உதாரணம்: Checkout service -> Payment service, Inventory service.

Payment service slow ஆனால் உங்களுக்கு தெரிய வேண்டும். அதற்கு உங்களுக்கு ஒரு SLI வேண்டும்.

அதை ஏன் தேர்வு செய்ய வேண்டும்?
* **Constraint-ஐ அடையாளம் காண:** Latency budget எவ்வளவு? Cost vs availability trade-off என்ன?
* **Prioritize செய்ய:** எந்த bug உண்மையில் user experience-ஐ கெடுக்கிறது?
* **Communicate செய்ய:** Product, SRE, business அனைவரும் ஒரே language பேசுவார்கள்.

Alternatives? Log grep செய்து "இன்று 10 errors வந்தது" என்பது reactive. SLI proactive.

## 5. Trade-offs

SLI தேர்வு என்பது எப்போதும் trade-off.

* **Availability vs Latency:** 99.99% availability வைக்க, you might increase timeout and retry. அது latency-ஐ அதிகரிக்கும். p95 good ஆ இருக்கும், p99 கெட்டுப் போகும்.
* **Granularity vs Noise:** Per endpoint SLI வைத்தால் visibility அதிகம், alert fatigue வரும். Aggregate SLI வைத்தால் problems hide ஆகும்.
