# PII

> **Learning Path:** Responsible AI & Governance
> **Section:** 22.1.5 — Learn

## 1. Problem

உங்க company-ல customer support chatbot build பண்றீங்க. User அவரோட phone number, Aadhaar, email சொல்லி "என்னோட account status என்ன?"ன்னு கேக்கறார்.

Chatbot அந்த conversation-ஐ log பண்ணுது. அதை training data-க்கு பயன்படுத்துறீங்க. RAG pipeline-ல document-ஆ store பண்ணீங்க. LLM prompt-ல direct-ஆ அனுப்புறீங்க.

ஒரு நாள் audit வருது. "நீங்க PII-ஐ எங்க store பண்ணீங்க? யாருக்கு access? data retention policy என்ன? consent இருக்கா?"ன்னு கேக்குது.

இப்போ தெரியுது, PII என்பது வெறும் "personal data" இல்லை. இது legal liability, breach risk, trust issue.

> What goes wrong if we don't have this? Data leak ஆனால் fine, reputation loss, user trust போகும். Model training-ல data leak ஆனால் sensitive info regenerate ஆகும்.

## 2. Mental Model

PII = Personally Identifiable Information. ஒரு நபரை uniquely identify பண்ண முடியும் அளவுக்கு போதுமான information.

Mental model simple: **Identity = risk**.

ஒரு data point தனியா harmless-ஆ இருக்கலாம். Combination-ல dangerous ஆகும்.

Name + City = maybe okay. Name + Phone + Aadhaar = PII.

AI system-ல PII-க்கு special treatment வேணும், because LLM remembers patterns, logs persist, vector database-ல embedding-ல leak ஆகும்.

## 3. How It Works

PII handling என்பது 3 layers.

**1. Identify**
Data classification. Input, output, logs, embeddings, training data, vector DB எல்லாத்துலயும் PII இருக்கான்னு detect பண்ணணும்.

Tools: regex, NER models, PII detection APIs. Eg: email, phone, PAN, Aadhaar, credit card.

**2. Control**
என்ன செய்யணும்? Options:
- Redact / Mask: `phone: +91-XXXXXXXX12` → `+91-********12`
- Tokenize: real value-ஐ vault-ல வச்சு token replace பண்ணு
- Remove completely
- Encrypt at rest + in transit, with access control

LLM prompt-ல போகும் முன் scrub பண்ணணும். RAG retrieval-ல PII document வரக்கூடாது.

**3. Governance**
Policy: retention, consent, purpose limitation, access audit.

Technical controls: data lineage, labeling, access policy, audit logs.

## 4. Architectural Reasoning

When does PII become architectural problem?

Customer-facing AI agent, support bot, fraud detection, healthcare, finance, hiring.

Constraints:
- Latency: real-time detection overhead
- Accuracy: false positive redaction kills user experience
- Compliance: GDPR, DPDP Act India, HIPAA
- Cost: PII vault, tokenization infrastructure

Options:
A. **Client-side redaction**: app layer-ல detect & mask. Fast, but client can bypass.
B. **Gateway scrubber**: API gateway-ல central PII filter. Single point of control, good for observability.
C. **Post-processing**: logs-ல detect & redact. Simpler, but data already leaked to LLM.

Architect choose Gateway scrubber + vault tokenization for high-risk flows. Low-risk internal analytics-க்கு post-processing enough.

Decision driver: **data sensitivity × exposure surface**.

## 5. Trade-offs

**Detection vs UX**
Strict redaction improves safety, but over-redaction breaks context. "My Aadhaar ending 1234" redact ஆனால் agent help பண்ண முடியாது.

**Centralization vs Latency**
Central PII service gives consistent policy, but adds network hop. Edge detection fast, but policy drift.

**Retention vs Utility**
Logs வச்சா debugging easy. But logs-ல PII இருந்தா retention risk. Trade-off: short retention + automatic scrub.

**Compliance vs Model Quality**
Training data-ல PII remove பண்ணா model quality drop ஆகலாம். But using PII for training without consent = legal risk.

Failure mode: LLM hallucination-ல PII regenerate. Detection didn't catch because user paraphrased phone number. Need output filtering too.

## 6. Practical Example

Enterprise HR assistant chatbot.

Flow:
User: "என்னோட salary slip-க்கு PAN number AA1234B இருக்கா?"
1. Gateway receives request.
2. PII detector flags PAN pattern.
3. Policy check: HR agent allowed to see PAN for authenticated user only. User authenticated? Yes.
4. Tokenize PAN → `PAN:<token_abc123>`. Real value goes to vault, token goes to LLM.
5. LLM responds with salary info, no raw PAN in logs.
6. Response filter checks output for leaked PII before sending to user.

If unauthenticated user asks same, request rejected or PAN redacted before LLM sees.

RAG documents: employee handbook vector DB. Documents labeled `contains_PII = true`. Retrieval policy blocks those chunks for external users.

## 7. Reasoning Challenge

உங்க RAG system-ல customer support tickets store பண்ணீங்க. Tickets-ல email, phone, order ID இருக்கு. Model-க்கு context வேணும், அதனால ticket text-ஐ direct-ஆ retrieve பண்ணறீங்க.

Now compliance team says "PII-ஐ vector DB-ல வைக்கக் கூடாது". 

உங்களுக்கு 2 options:
1. All tickets-ஐ scrub பண்ணி store பண்ணு. 
2. PII-ஐ tokenize பண்ணி store பண்ணு, real value vault-ல.

நீங்க எதை தேர்வு செய்வீங்க? ஏன்? Trade-off என்ன?

## 8. Key Takeaways

- PII handling is architectural, not just regex. Identify → Control → Govern.
- LLM system-ல PII leak ஆகும் surface area பெருசு: input, prompt, logs, embeddings, outputs.
- Central gateway scrubbing + tokenization gives auditability, but adds latency and complexity.
- Every redaction decision is a trade-off between safety, UX, and model utility.

இது ஏன தேவைன்னு புரிஞ்சுது. எப்போ use பண்ணணும், எதுக்காக choose பண்ணுறோம்னு reason பண்ண முடியும்.
