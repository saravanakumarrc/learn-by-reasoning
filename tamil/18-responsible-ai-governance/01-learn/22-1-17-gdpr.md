# GDPR

> **Learning Path:** Responsible AI & Governance
> **Section:** 22.1.17 — Learn

## 1. Problem

நீங்கள் ஒரு SaaS product-ஐ EU customers-க்கு விற்கிறீர்கள். Customer data Europe-ல இருந்து வருது. ஒரு நாள் user சொல்றார்: "என் data எல்லாம் என்ன செய்யறீங்க? என் data-வை delete பண்ணுங்க. எனக்கு copy வேணும்."

இப்போ team-ல கேள்வி வருது:

* எந்த database-ல எல்லாம் அவர் data இருக்கு?
* backup-ல இருக்கா?
* third-party service-களுக்கு அனுப்பியிருக்கோமா?
* delete செய்யணும்னா எப்படி track பண்ணுவது?

இதை ad-hoc-ஆ handle பண்ண முடியாது. Fine வரும். GDPR என்பது இந்த chaos-க்கு ஒரு system boundary கொடுக்கிறது.

**What goes wrong if we don't have this?** Data sprawl, legal risk, loss of trust, மற்றும் unpredictable cost.

## 2. Mental Model

GDPR என்பது ஒரு **data processing contract** between business and data subject. 

Core idea: Personal data என்பது user-க்கு சொந்தமானது. நீங்கள் processor / controller-ஆக இருந்து அதை handle பண்ணும்போது, lawful basis, transparency, minimization, security, மற்றும் accountability தேவை.

அதாவது: Collect less, use only for stated purpose, keep secure, allow access/deletion, and prove it.

## 3. How It Works

GDPR 7 core principles-ஆக இயங்குகிறது. Architect-க்கு முக்கியமானவை:

* **Lawful basis**: Consent, contract, legal obligation போன்ற valid reason இல்லாமல் data collect பண்ணக்கூடாது.
* **Purpose limitation**: ஒரு purpose-க்காக collect செய்த data-வை வேறு purpose-க்கு use பண்ண முடியாது.
* **Data minimization**: தேவையான data மட்டும் எடுக்கணும்.
* **Storage limitation**: Data-வை தேவைக்கு அதிகமாக keep பண்ணக்கூடாது.
* **Rights of data subject**: Access, Rectification, Erasure - Right to be Forgotten, Data Portability, Objection.
* **Security & Accountability**: Technical and organizational measures, DPIA, Records of Processing Activities.

Data subject request வந்தால் 30 days-க்குள் respond செய்யணும். இது operational SLA ஆகிறது.

## 4. Architectural Reasoning

GDPR useful ஆகும் போது:

* நீங்கள் EU data subjects-ன் personal data process பண்ணும்போது. இது location-அடிப்படையில் apply ஆகும், company location-அல்ல.
* Data sharing பண்ணும் ecosystem இருக்கும்போது. Controller vs Processor distinction முக்கியம்.

Alternatives? No GDPR = no market access to EU. So choice is not if, but how to comply.

Architect ஏன் choose பண்ணுவார்?

* Privacy by Design: Data collection point-லேயே minimization enforce செய்வது.
* Data mapping: Where data flows, who accesses, retention policy எது என்பதை தெரிந்து வைத்திருப்பது.
* Deletion capability: Logical delete போதாது, backups, logs, third-party stores வரை propagate செய்யணும்.

## 5. Trade-offs

**Compliance vs Velocity**
Privacy review, consent management, DPIA செய்வது release speed-ஐ slow ஆக்கும். ஆனால் retrofitting costly.

**Centralization vs Data minimization**
Central data lake எல்லா data-வும் கொடுக்கும். GDPR-க்கு purpose-specific stores, access control, audit trail தேவை. மிக அதிக centralization risk ஆகும்.

**Retention vs Availability**
Long retention = analytics, debugging easy. GDPR-க்கு storage limitation + right to erasure. இதனால் automated retention policies, data lifecycle management தேவை.

**Failure mode:** Right to Erasure request-ஐ நீங்கள் process பண்ணினாலும், third-party vendor அதை delete செய்யவில்லை என்றால் நீங்கள் liable. Data Processing Agreement தேவை, மற்றும் vendor audit.

## 6. Practical Example

Enterprise SaaS with EU customers.

Architecture:
* Ingestion service collects PII. Lawful basis record consent id-ஐயும் store செய்கிறது.
* PII Store is separate from analytics store. Tokenization / pseudonymization apply செய்யப்படுகிறது.
* Data Catalog with lineage: எந்த service, எந்த table, எந்த third-party-க்கு data flow ஆகிறது.
* Consent Management Service: consent grant/revoke events emit செய்கிறது. Event-driven architecture-ல downstream services listen செய்து data processing-ஐ stop செய்கிறது.
* DSR Orchestrator: Access / Erasure request வந்தால், data map-ல இருந்து affected stores-ஐ identify செய்து, delete jobs-ஐ trigger செய்கிறது. Audit log maintain செய்கிறது.

இப்படி design செய்யாவிட்டால், ஒரு delete request-க்கு 15 teams-க்கு manual email போக வேண்டியிருக்கும்.

## 7. Reasoning Challenge

உங்கள் system-ல user profile data database-ல இருக்கு, அதே data analytics warehouse-ல aggregate செய்யப்பட்டு, மற்றும் support logs-ல raw PII இருக்கு. User Right to Erasure request வந்தது. 

என்ன architecture decisions செய்வீர்கள்? Hard delete vs soft delete? Backups எப்படி handle பண்ணுவீர்கள்? Third-party analytics provider-க்கு என்ன சொல்வீர்கள்?

## 8. Key Takeaways

* GDPR என்பது legal requirement அல்ல, data lifecycle-க்கான architectural constraint ஆகும்.
* Privacy by Design, data mapping, மற்றும் verifiable deletion capability core system properties ஆகும்.
* Controller-Processor relationship, DPA, மற்றும் audit trail இல்லாமல் compliance prove செய்ய முடியாது.
* Every data collection decision creates future operational cost for access, portability, and erasure.
