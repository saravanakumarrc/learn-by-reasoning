# SQL

> **Learning Path:** Data Architecture
> **Section:** 4.1.2 — Databases

## 1. Problem

உங்களுக்கு ஒரு e-commerce system இருக்கு. Orders, customers, products என்று data உள்ளது. 

இப்போது business team கேட்கிறது: "கடந்த 30 நாளில் Chennai-ல இருந்து வந்த orders-ல average order value எவ்வளவு?" 

ஒரு engineer போய் code-ல loop போட்டு filter பண்ணி calculate பண்ணலாம். ஆனால் அடுத்த நாள் கேள்வி வரும்: "return பண்ணப்பட்ட orders-ஐ எடுக்காதே". அடுத்த நாள்: "product category-வாரியாக breakup வேண்டும்".

இப்படி ஒவ்வொரு query-க்கும் application code மாற்ற வேண்டியிருக்கும். Data storage format மாறினால் எல்லா service-மும் உடைந்து விடும். Multiple teams ஒரே data-ஐ வெவ்வேறு விதமாக access பண்ணும்போது inconsistency வரும்.

இந்த pain-தான் SQL-க்கு வேர்.

## 2. Mental Model

SQL என்பது database-க்கு கொடுக்கப்படும் **declarative contract**. நீங்கள் *என்ன* வேண்டும் என்பதை சொல்லுங்கள், *எப்படி* கண்டுபிடிப்பது என்பதை database பார்த்துக்கொள்ளும்.

Mental model எளிது: Table = spreadsheet. Row = one entity. Column = attribute. Primary key = unique identity.

நீங்கள் application-ல இருந்து procedural code எழுதுவதற்கு பதில், ஒரு common language-ல question கேட்கிறீர்கள். அதை எந்த relational database implement பண்ணினாலும் புரிந்து கொள்ளும்.

## 3. How It Works

SQL இரண்டு விஷயங்களை செய்கிறது:

**Schema definition:** `CREATE TABLE`, `PRIMARY KEY`, `FOREIGN KEY`, `INDEX`. இது data shape-ஐ enforce பண்ணும். ஒரு order எப்போதும் customer_id-ஐ reference பண்ண வேண்டும் என்பதை database-யே காப்பாற்றும்.

**Query language:** `SELECT`, `WHERE`, `JOIN`, `GROUP BY`. இது set-based thinking. நீங்கள் collection-ஐ மொத்தமாக describe பண்ணுகிறீர்கள், ஒவ்வொரு row-ஐயும் loop பண்ணச் சொல்லவில்லை.

Database optimizer உள்ளே index use பண்ணுமா, full scan பண்ணுமா என்று decide பண்ணும். Application-க்கு அந்த detail தேவையில்லை.

## 4. Architectural Reasoning

SQL எப்போது useful?

* Data க்கு **strong consistency** தேவை. Financial transactions, inventory, user accounts போன்ற இடங்களில்.
* Multiple services, multiple teams ஒரே source of truth-ஐ access பண்ண வேண்டும். SQL ஒரு standard interface கொடுக்கிறது.
* Ad-hoc analysis, reporting தேவை. Business user கூட basic query புரிந்து கொள்ளலாம்.
* Relationships முக்கியம். Orders -> Customers -> Products என்று join பண்ண வேண்டும்.

Alternatives உள்ளன: NoSQL document store, key-value store. அவை schema flexibility மற்றும் horizontal scale-ல் நல்லது. ஆனால் ad-hoc joins, complex filtering கடினம்.

Architect-ஆக நீங்கள் கேட்க வேண்டியது: Data shape stable-ஆ? Relationships important-ஆ? Team-க்கு SQL skill இருக்கா? இவை Yes என்றால் SQL natural choice.

## 5. Trade-offs

**Consistency vs Flexibility:** SQL schema rigid. Field add பண்ண ஒரு migration தேவை. NoSQL-ல் அது எளிது. ஆனால் rigidity தான் data integrity-க்கு உதவுகிறது.

**Read complexity vs Write simplicity:** Complex joins மற்றும் aggregations SQL-ல் easy. ஆனால் very high write throughput, highly dynamic schema scenarios-ல் overhead ஆகும்.

**Operational complexity:** Primary key design தவறினால் hotspot வரும். Index மிக அதிகமானால் write slow ஆகும். `N+1 query` போன்ற failure modes application layer-ல் வரும்.

**Scale pattern:** Vertical scale முதலில் எளிது. Horizontal scale-க்கு sharding தேவை, அது application-ஐ complex ஆக்கும்.

## 6. Practical Example

Order service.

```sql
CREATE TABLE orders (
  order_id UUID PRIMARY KEY,
  customer_id UUID NOT NULL,
  order_ts TIMESTAMP NOT NULL,
  amount DECIMAL NOT NULL,
  city VARCHAR NOT NULL
);

CREATE INDEX idx_orders_ts_city ON orders(order_ts, city);
```

இப்போது business query:

```sql
SELECT AVG(amount) 
FROM orders 
WHERE order_ts >= NOW() - INTERVAL '30 days' 
  AND city = 'Chennai' 
  AND status = 'paid';
```

இந்த query-ஐ எந்த service-ல இருந்தும் எந்த tool-ல இருந்தும் கேட்கலாம். Storage engine B-tree index use பண்ணி fast ஆக்கும். நீங்கள் loop எழுத வேண்டாம்.
